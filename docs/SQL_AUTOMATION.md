# Автоматичний запуск SQL у робочій базі (з 2026-11-07)

Рішення власника 2026-11-07: замість «відкрити файл → скопіювати → SQL Editor → Run» SQL-файли запускає GitHub Actions після мержу PR, **лише після «Approve» власника**.

## Як це працює

1. Claude готує PR: нові файли в `supabase/migrations/` (схема) і `supabase/data_fixes/` (контент), тести в `supabase/tests/`. В описі PR — які файли запустяться і що змінять.
2. На PR працює CI (`ci.yml`): ті самі файли застосовуються на чистій тестовій базі в GitHub, проходять усі SQL-тести, lint, збірка.
3. Власник робить Merge → запускається workflow **Apply SQL (production)** (`.github/workflows/db-apply.yml`):
   - job **plan** (без доступу до бази) показує в Summary, які SQL-файли й тести змінились;
   - job **apply** чекає кнопки **Review deployments → Approve**; лише після неї отримує секрет `SUPABASE_DB_URL` і запускає `scripts/db/apply.sh`.
4. `scripts/db/apply.sh`:
   - журнал `ops.sql_journal` (міграція M20): який файл, коли, яким запуском — **кожен файл запускається один раз**;
   - спершу `migrations/`, потім `data_fixes/`, за назвою (дата на початку назви);
   - файл з власними `begin; … commit;` — як є, інакше однією транзакцією; **перша помилка зупиняє все** (файл відкочується, наступні не запускаються, у журнал не пишуться);
   - уже запущений файл, який потім змінили, не запускається вдруге (попередження в Summary) — зміна завжди новим файлом;
   - тести, змінені в цьому push, — кожен має вивести `ALL TESTS PASSED` (транзакція + `ROLLBACK`, дані не лишаються).
5. Результат — в Actions → запуск → Summary: повідомлення «Готово: …» кожного файлу і тести.

Файли, що були в репозиторії до автоматизації (запущені вручну або свідомо не запускались — замінені частинами / новішими пакетами), перелічені в `supabase/sql_journal_baseline.txt`: вони позначаються як `baseline` і **ніколи** не запускаються. Нові файли туди не додавати.

Вручну: Actions → **Apply SQL (production)** → **Run workflow** (поле «тести»: імена файлів, `all` або порожньо) → Approve.

## Налаштування (власник, один раз)

1. **Адреса бази.** Supabase → проєкт «New app for learning» → кнопка **Connect** → **Session pooler** → скопіювати URI (`postgresql://postgres.mhdgozragkkogvxpjksp:[YOUR-PASSWORD]@…pooler.supabase.com:5432/postgres`) і вставити пароль бази замість `[YOUR-PASSWORD]`. Session pooler — бо GitHub Actions не дістає прямої адреси бази (лише IPv6). Якщо в паролі є `@ : / ? # %` — краще змінити пароль бази на літери й цифри (Project Settings → Database; застосунок працює з ключами API, тож його це не зачепить).
2. **Середовище з підтвердженням.** GitHub → репозиторій → **Settings → Environments → New environment** → назва `production` → **Required reviewers**: `sergeygavrilyk` → **Save protection rules**. («Prevent self-review» не вмикати — мерджить і підтверджує той самий власник.) За бажанням: **Deployment branches** → лише `main`.
3. **Секрет.** Там само, у середовищі `production` → **Environment secrets → Add secret**: назва `SUPABASE_DB_URL`, значення — адреса з п. 1. Секрет бачить лише job, який власник підтвердив; Claude і PR з інших репозиторіїв його не бачать.
4. Перший запуск після мержу цього PR застосує лише M20 (журнал) і позначить 170 старих файлів як `baseline`.

## Правила для Claude

- З робочої бази — лише читання; запис — тільки через цей workflow (Approve власника) або з явного дозволу власника на кожен запуск (рішення 2026-11-06).
- Не запускати workflow самому і не змінювати `sql_journal_baseline.txt` без рішення власника.
- В описі PR: список SQL-файлів, що запустяться, очікувані повідомлення «Готово…», тести.
