# Офлайн без втрат: прогрес зберігається, коли немає мережі (план, 2026-11-16)

> Статус: **рішення прийнято 2026-11-16** (розділ 10: етап 1, потім 2; `client_ops` — так; 14 днів; серія за днем навчання — так; тексти — «Добро»). Етап 1 — PR #50. **Відмінності реалізації від плану:** хук — `components/OfflineSync.tsx` (а не `useOfflineSync.ts`); номер дії сервер записує в `client_ops` **після** того, як дію застосовано (а не до) — інакше збій посередині загубив би дію; понад 200 дій першими відкидаються події навчання, а не прогрес; до запуску M28 сервер приймає чергу без журналу. Пов'язано: §76 (`ARCHITECTURE.md`), PR #48 (сторінка більше не перезавантажується сама, коли повертається мережа).

## 1. Навіщо

§76 обіцяє: уроки, вправи, повторення (SRS) і **прогрес** працюють без мережі. Зараз відкрити урок чи текст без мережі можна, але **результат губиться**:

| Дія | Що зараз без мережі | Де в коді |
|---|---|---|
| Урок пройдено | «Не вдалося зберегти прогрес — перевірте інтернет»; урок не позначено, слова не йдуть у повторення, серія 🔥 не рахується | `LessonPlayer` → `completeLesson` (`app/actions/progress.ts`) |
| Текст прочитано, відповіді на питання | «Немає інтернету — результат не збережено» | `ReadingScreen` → `completeReading` |
| Слово з тексту / словника → у повторення | «Немає інтернету — спробуйте пізніше» / «Не вдалося додати слово. Перевірте інтернет» | `saveReadingWord`, `saveDictionaryWord` |
| Події навчання (`exercise_completed`, `lesson_started`…) | губляться мовчки — «Успішна навчальна сесія» (North Star) недораховується | `track()` (`lib/analytics-client.ts`) |
| Тренажер повторень | **не відкривається**: картки беруться з бази прямо в браузері | `app/trainer/page.tsx` |
| «Помилки», «Типові помилки» | «Не вдалося зберегти відповідь» (помилка повториться — прийнятно) | `rateMistake`, `answerTypicalError` |
| Перевірка рівня | відповіді лишаються на екрані, «спробуйте ще раз» — уже нормально | `AssessmentPlayer` |

Людина пройшла урок у метро — і втратила результат. Для застосунку, яким користуються в дорозі, це головна прогалина офлайну.

## 2. Як роблять у світі

- **Duolingo** (за описами користувачів): завантажені уроки проходять без мережі, бали й серія днів зберігаються на телефоні й синхронізуються, щойно з'являється інтернет; посеред уроку нічого не перезавантажується.
- **Загальна практика «offline-first»:** спершу записати на пристрій, інтерфейс відповідає одразу, а відправлення на сервер — у фоні, коли є мережа. Що не відправилось — у чергу, повторити пізніше. Людині показують стан («Офлайн», «Синхронізую…»), а не помилку.
- **iPhone:** вбудованої фонової синхронізації браузера (Background Sync) у Safari немає, тому відправляємо, коли з'явилась мережа або застосунок знову відкрили — так роблять усі, хто підтримує iPhone.

## 3. Що пропоную (простими словами)

1. Коли без мережі людина завершує урок, текст, додає слово чи навчальна подія не відправилась — застосунок **кладе це в чергу на телефоні** і каже: «Урок пройдено! Прогрес збережемо, щойно з'явиться інтернет».
2. Щойно мережа є (подія «мережа з'явилась», відкриття застосунку, повернення у вкладку), черга **тихо відправляється** по одній дії, у тому порядку, як людина вчилася.
3. Сервер приймає кожну дію **рівно один раз** (у кожної дії свій номер), навіть якщо телефон надіслав її двічі.
4. Серія 🔥 і «повторити завтра» рахуються за **днем, коли людина справді вчилася**, а не коли з'явилась мережа.
5. Нічого не перезавантажується і не перериває урок.

## 5. Як це влаштовано (етап 1)

**Черга на телефоні** — `lib/offline-queue.ts` (логіка без браузера, з тестами) + хук `components/useOfflineSync.ts` у кореневому layout.

- Запис черги: `{ op_id (uuid), kind, user_id, at (час дії на телефоні), payload }`. Види: `lesson_completed`, `reading_completed`, `word_saved`, `event`.
- Сховище — `localStorage` (як офлайн-копії уроків, без нових залежностей), ключ із `user_id`: черга одного акаунта ніколи не піде від імені іншого.
- Межі (рішення 10.3): не більше 200 дій і не старші 14 днів; старші — відкидаємо й кажемо про це людині.
- Пошкоджена черга (зламаний JSON, невідомий вид) — відкидаємо запис, застосунок не падає (як `parseOfflineCopy`).

**Відправлення** — один server action `syncOfflineOps(ops)` пакетом до 20 дій:

- авторизація як зараз (`requireLearningContext`); дія чужого `user_id` — не приймається, лишається в черзі до входу «свого» акаунта;
- кожна дія спершу записується в журнал `client_ops` (номер унікальний) — повтор того самого номера сервер мовчки пропускає;
- час дії: якщо в майбутньому — беремо час сервера, якщо старший за 14 днів — відмова; далі ту саму логіку, що й онлайн, викликаємо з цим часом (`completeLesson(..., now: at)`, `completeReading`, події з `occurred_at = at`);
- відповідь по кожній дії: прийнято / вже було / відмова (з причиною) — телефон прибирає з черги прийняті й відмовлені, решту пробує пізніше (пауза 5 с → 30 с → 2 хв).

**Онлайн нічого не змінюється:** дія відправляється одразу, як зараз; у чергу потрапляє лише те, що не відправилось.

**Конфлікти:** урок, пройдений на двох пристроях, — один рядок (`upsert`), лишається **раніша** дата; слово вже в повторенні — не чіпаємо (як зараз). Оцінки карток (етап 2) застосовуємо за часом дії по черзі.

## 6. Що бачить людина (чернетки текстів — UX, на «ок»)

- Святковий екран без мережі: «Урок пройдено! 🎉 Прогрес збережемо, щойно з'явиться інтернет» — замість червоної помилки. Серію 🔥 без мережі не показуємо (точне число — після синхронізації).
- Текст: «Результат збережемо, щойно з'явиться інтернет».
- Маленький значок угорі на «Сьогодні» й «Уроках», лише коли є що відправити: «⏳ 2 результати чекають на інтернет». Після відправлення — коротко «✓ Прогрес збережено» і значок зникає.
- Черга старша за 14 днів: «Частину результатів без інтернету старших за 14 днів не вдалося зберегти» — один раз.

## 7. База даних (PROPOSE — нова таблиця)

Міграція **M28** (адитивна, ідемпотентна, з RLS):

```sql
create table if not exists public.client_ops (
  op_id       uuid primary key,                 -- номер дії з телефону
  user_id     uuid not null references auth.users(id) on delete cascade,
  kind        text not null check (kind in ('lesson_completed','reading_completed','word_saved','event','srs_rating')),
  occurred_at timestamptz not null,             -- коли людина це зробила
  received_at timestamptz not null default now()
);
-- RLS: insert / select лише своїх (auth.uid() = user_id); update і delete — заборонено (журнал append-only)
```

- Таблиця маленька (лише номери, без змісту); старше 30 днів можна чистити пізніше (окреме рішення).
- `lesson_progress.completed_at` — дата не переписується пізнішою (правка в `markLessonCompleted`, без зміни схеми).
- `reading_progress.read_count` — повтор дії не додає читання (захищає журнал `client_ops`).

## 9. Тести

- **Unit** `lib/offline-queue.test.ts`: додати / прочитати / прибрати, порядок за часом, той самий `op_id` двічі — один запис, межі 200 / 14 днів, чужий `user_id` не віддається, пошкоджене сховище й невідомий вид — без падіння, пауза між спробами.
- **Unit** для серверної частини (у `lib/`): час з майбутнього → час сервера, старше 14 днів → відмова, повтор номера → «вже було».
- **SQL** `client_ops.test.sql`: свої рядки бачить лише власник, чужий `user_id` не вставити, повтор `op_id` не вставити, update / delete заборонено, гість без доступу.
- **E2E** (`user.spec.ts`, у збірці): без мережі пройти тестовий урок → «Прогрес збережемо…» → увімкнути мережу → значок зник, у «Уроках» урок позначено пройденим. Те саме для тексту.

## 11. Ризики

- Людина вийшла з акаунта, поки черга не відправилась, — черга чекає входу того самого акаунта (на спільному телефоні чужий акаунт її не відправить).
- Очищення даних браузера стирає чергу — так само, як і зараз офлайн-копії уроків; попереджати не будемо.
- Годинник телефона неправильний — захищає межа «не з майбутнього / не старше 14 днів».
